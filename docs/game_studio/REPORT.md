# Game Studio dans APEX — qualification cloud de la mission #18

Le parcours Game Studio est maintenant accessible dans la navigation du frontend APEX existant. Il crée une vraie mission `MissionService`, exécute les scripts Blender de Game Graphics avec le modèle local, archive chaque version dans `ArtifactStore` et affiche les jugements et les fichiers. Le build runtime copie le frontend, les modules et les scripts dans la distribution utilisée par le launcher. **Le launcher Windows lui-même n'a pas été exécuté dans ce cloud Linux.**

La branche réservée #18 est empilée dans l'ordre sur les commits de #11 (orchestration), #12 (Game Graphics), #13 (Game Engineer), #16 (connecteur graphique UE5) et #17 (opérations Blender, familles et TripoSR). Aucune de ces PR n'a été fusionnée vers `apex/integration` ou `main`, et les fichiers du cerveau Claude n'ont pas été modifiés.

## Correction visuelle intégrée, défaut injecté explicitement

Une seconde mission API de fauteuil, `836f8046-aac5-45db-9b89-1b851ad82811`, a créé une référence Blender jugée `PASS` après une calibration visuelle native [conservée ici](evidence/chair/calibration.json) : quatre vrais positifs, quatre vrais négatifs, aucun faux positif ou négatif dans ce petit banc. Un banc de diagnostic isolé a ensuite injecté **hors de l'interface utilisateur**, avec le catalogue Blender réel, un décalage de +0,12 m sur `arm_left`. Il a porté le budget de une à trois tentatives et activé les corrections dans le reçu de cette mission de diagnostic avant la reprise ; cette modification du reçu ne fait pas partie du parcours utilisateur normal. La révision défectueuse possède son `.blend`, son `.glb` et quatre rendus ; le juge calibré a signalé deux défauts `paired_component_alignment` de 0,12 m sur les vues de face et arrière, et a rendu `FAIL`.

L'API de reprise a gardé le même identifiant Game Studio et créé une nouvelle mission APEX liée. Le juge a fourni au contrôleur Qwen la cible et la position absolue de référence. Le plan accepté [n'a déplacé que `arm_left` vers `[0, 0, 0]`](evidence/chair/plan.json), puis Blender a sauvegardé une troisième version et le juge a rendu `PASS`, sans défaut restant. La [capture du défaut](evidence/chair/game-studio-defect.png) et la [capture de la correction](evidence/chair/game-studio-corrected.png) viennent du frontend APEX rendu dans Chromium : 12 images téléchargées par l'API, sans échec réseau ni erreur de page. Les projets et les quatre vues des versions défectueuse et corrigée sont dans `evidence/chair/`.

La [comparaison structurée](evidence/chair/scope-verification.json) confirme que la géométrie de l'accoudoir, les autres objets et les paramètres de rendu ont gardé les mêmes empreintes ; seule la position ciblée est passée de `z=0,12` à `z=0`. Le rendu Blender a pris 96,73 s pour la référence, 94,10 s pour le défaut et 96,69 s pour la correction ; pics RSS échantillonnés respectifs de 325,54, 315,88 et 329,12 Mio. Qwen CPU a atteint 7,69 Go RSS après génération, puis son processus a été arrêté et vérifié. Les versions, verdicts et mesures figurent dans [la réponse API](evidence/chair/correction-api-result.json) et les `execution.json` de chaque version. Cette preuve qualifie une **correction locale d'alignement sur ce fauteuil et ces vues**, pas un jugement général de beauté ou une réparation universelle.

Une mission de fauteuil `a1933f4e-9776-4ca3-99c0-e05f6cef51f5` a aussi été annulée via HTTP pendant Blender : état final `cancelled`, processus enfant arrêté et vérifié dans `execution.json`. Le job de voiture a été repris après interruption avec le même identifiant stable et une nouvelle entrée `mission_history`.

## Contrats intégrés

`GET /api/v1/game-studio/capabilities` expose les dépendances observées et les états `available_validated`, `available_unqualified`, `blocked_dependency` ou `not_implemented`. `POST /api/v1/game-studio/missions` accepte le type, style, niveau, outil, modèle, backend de calcul, description, deux options indépendantes de juges/corrections, budgets, critères et références avec provenance. `GET /missions`, `GET /missions/{id}`, `POST /missions/{id}/cancel`, `POST /missions/{id}/resume` et `GET /missions/{id}/artifacts/{hash}` exposent l'état, les versions et les octets. Toutes ces routes réutilisent l'authentification uniforme de l'API APEX ; les références PNG/JPEG/texte sont limitées et validées avant stockage. Le chemin `C:\GameProject` reste refusé.

Le spécialiste utilise `ModelProvider` pour la génération locale, le catalogue autorisé et `ToolEngine` pour enregistrer les plans, `MissionService` pour le cycle de vie, `ArtifactStore` pour les preuves, le juge Game Graphics et `RecoveryPolicy` pour les rejets bornés. Il ne crée pas de second jugement généraliste. `TaskLoop` et `Scheduler` n'exécutent pas encore la mission Blender ; le connecteur de #11 concerne un autre type de tâche. Les projets et Workspaces APEX ne sont pas encore associés à chaque job Game Studio : le stockage actuel est le dossier standalone `.apex/game-studio/missions` avec contrôle de chemin.

## Vérifications et limites

La construction frontend et ses 173 tests passent. Les tests backend ciblés couvrent authentification, validation des références et critères, contrats Blender/UE, et filtrage du plan Qwen. Le build runtime et `runtime_build.verify` passent ; les scripts Game Graphics et leur benchmark sont inclus. La capture Chromium vérifie le frontend rendu et les images issues de l'API authentifiée. Le binaire `apex.exe`, son installation, CUDA, TripoSR GPU et UE5.8 restent non qualifiés faute d'accès à Windows/GPU/éditeur. Le connecteur UE5 de #16 garde l'état BLOCKED ; aucune scène Unreal n'est annoncée. Le diagnostic TripoSR vérifie la présence de ses quatre entrées locales ; elles sont absentes ici. Même si elles et CUDA étaient disponibles, le dispatch neuronal depuis une mission Game Studio resterait `not_implemented`. Le contrat Game Engineer de #13 est présent dans le paquet mais son dispatch depuis Game Studio reste lui aussi `not_implemented`.

Les styles autres que « réaliste », les environnements, le monde ouvert et l'hybride restent non implémentés dans le parcours intégré. Les références image sont archivées mais le contrôleur texte ne lit pas leurs pixels. Les niveaux « Jouable », « Soigné » et « Photoréaliste » conservent leurs contrats et leurs contrôles, sans qualification artistique complète. La case « juges sur toutes les tâches » transmet le verdict au contrôleur et juge chaque révision ; elle ne constitue pas encore une inspection spécialisée de chaque sous-opération. Les corrections automatiques sont bornées et indépendantes de cette case. Le modèle natif APEX est détecté via `ModelProvider`, sans qualification de qualité dans ce lot. Aucune adaptation de poids n'a été exécutée.

Prochaine expérience utile : une création utilisateur présentant spontanément un défaut d'alignement détectable, sans injection de diagnostic, pour mesurer la fréquence de succès de cette correction. Qualifier ensuite le parcours `apex.exe` et la voie CUDA sur le PC Windows disponible.
