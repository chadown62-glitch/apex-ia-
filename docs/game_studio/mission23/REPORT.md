# Mission #23 — planification Game Studio et contrat véhicule

Cette branche part du commit `c0a85919bba6bcf724c9caa0a2b984ac4c535369` de la PR #22. Elle conserve `MissionService` pour l'état des missions et `ArtifactStore` pour les fichiers. Le modèle local Qwen propose un graphe borné ; le validateur contrôle le schéma, les types, les dépendances, les cycles, le budget et les capacités avant de lancer Blender. Aucun code ni chemin fourni par le modèle n'est exécuté. Les missions de recette `garage-v1` déjà enregistrées restent consultables.

## Plans réellement générés

Les trois sorties brutes de Qwen sont [plan 1](plan-1.json), [plan 2](plan-2.json) et [plan 3](plan-3.json). [L'évaluation](plan_evaluation.json) conserve leurs empreintes, les rejets et le résultat du validateur final : quatre assets puis assemblage pour deux voitures, une galerie et un fauteuil ; fauteuil seul ; façade puis transfert Unreal bloqué. Le troisième essai avait été refusé par le validateur initial parce que Qwen avait nommé le transfert `unsupported` malgré sa dépendance. Le validateur final normalise ce cas précis en `unreal_handoff` seulement si Unreal a été demandé, puis conserve son statut bloqué. Les autres normalisations acceptées sont limitées aux identifiants numériques/camelCase et aux descriptions d'exigences non satisfaites ; les tâches, dépendances, budgets et permissions restent contrôlés.

La faisabilité publiée porte sur les capacités connues et le graphe, **pas** sur la couverture sémantique de l'objectif. Qwen a par exemple remplacé une galerie demandée par un garage dans le premier plan : ce défaut reste visible dans la trace et interdit de qualifier ce plan de fidèle. Les références visuelles sont conservées avec provenance, mais leur contenu n'est pas encore interprété.

Un essai véhicule naturel a aussi produit [un mauvais plan](evidence/rejected-vehicle-component-plan.json) : une tâche `vehicle` pour la carrosserie et une autre tâche `vehicle` pour les roues d'une **seule** voiture. Il a été arrêté, puis le validateur a été renforcé pour comparer le nombre de tâches véhicule au nombre de voitures explicitement demandé. Le même plan brut donne désormais `vehicle_components_must_remain_inside_one_vehicle_asset`. Cette règle ne prétend pas résoudre toute la couverture sémantique.

## Véhicule Graphics → Engineer

Le projet intégré `e70ad228-c457-4dca-88bd-2c1387877e6d` a créé une vraie [voiture Blender](evidence/vehicle-integrated/vehicle.blend) et son [GLB corrigé](evidence/vehicle-integrated/vehicle.glb). Une opération Blender bornée crée quatre roues racines nommées selon `VehicleAssetContract v1`, rattache les jantes, moyeux et rayons à leurs roues, mesure leurs pivots, axes et dimensions, sauvegarde une nouvelle version puis réexporte le GLB. Le même précontrôle examine les octets du nouvel export et donne [PASS](evidence/vehicle-integrated/engineer-report.json). La vérification complémentaire des données réellement exportées trouve `wheel_slot` sur les quatre nœuds GLB et 12 enfants visuels par roue : [rapport](evidence/vehicle-integrated/engineer-report-extra-check.json), [métadonnées](evidence/vehicle-integrated/vehicle-contract.json). Le [reçu parent](evidence/vehicle-integrated/project-receipt.json) conserve FAIL, PASS, mesures et artefacts des deux versions. Ce résultat valide le **transfert de l'asset**, pas son import UE5, ses collisions ou sa physique.

Les deux réponses brutes et leurs temps mesurés sont conservés.

## Mission multi-assets exécutée dans APEX

Projet isolé `3712b584-b5d4-4f5d-bc8c-e47436bf2479`, objectif inédit : « Crée une vitrine de fleuriste de quartier avec un fauteuil d'accueil et assemble un décor de rue ». Le [reçu parent](evidence/project-receipt.json) contient le plan Qwen à trois tâches, deux véritables missions Game Graphics et une scène assemblée, toutes en `review` avec livraison `technical_review` après 585,28 s au total. Les [sorties brutes du plan](evidence/demo-planner-trace.json) ont été validées avant Blender. Une reprise après un rejet de graphe a réutilisé la réponse validée sans régénérer le plan. Les tentatives précédentes et leur raison figurent dans l'historique du reçu.

Le bâtiment avait un défaut **naturel** sur `atelier_letters` : 2 faces dégénérées et 3 normales invalides dans BLEND et GLB. Le [juge initial](evidence/building-before/judge-report.json) l'a refusé ; [Qwen a choisi](evidence/building-correction-plan.json) la réparation de cet objet seul, puis [le second jugement](evidence/building-after/judge-report.json) a accepté le résultat. Les rendus [avant](evidence/building-before/front_three_quarter.png) et [après](evidence/building-after/front_three_quarter.png) sont conservés, mais la progression prouvée est topologique. Le fauteuil a deux versions [avant](evidence/chair-before/front_three_quarter.png) et [après](evidence/chair-after/front_three_quarter.png) : Qwen a modifié son matériau PBR, sans mesure esthétique calibrée permettant d'affirmer que ce coloris est meilleur.

Les projets Blender et GLB sélectionnés sont dans [bâtiment](evidence/assets/building/asset.blend) et [fauteuil](evidence/assets/chair/asset.blend). La [scène Blender](evidence/scene/garage.blend) et son [GLB](evidence/scene/garage.glb) ont été produits par import des deux assets. Quatre rendus natifs sont livrés : [trois-quarts](evidence/scene/front_three_quarter.png), [arrière](evidence/scene/rear_three_quarter.png), [côté](evidence/scene/side.png), [dessus](evidence/scene/top.png). Le [rapport de réouverture](evidence/scene/reopen-report.json) confirme un second processus Blender, 143 meshes de bâtiment, 32 meshes de fauteuil, la route, le trottoir, une caméra et trois lumières. Le [rapport de cadrage](evidence/scene/framing-report.json) montre un défaut géométrique initial sur la vue trois-quarts, corrigé automatiquement en deux élargissements de caméra, puis quatre vues qui gardent les objets source dans le champ. Ce contrôle ne mesure ni la beauté ni toutes les occlusions.

L'API authentifiée a retourné le projet en HTTP 200 et le PNG de scène avec un SHA256 conforme à ArtifactStore. Chromium a ouvert la [page Game Studio réelle](evidence/ui-project.png), affiché le plan, les tâches, les verdicts et 20 rendus sans erreur JavaScript ; [contrôle API/UI](evidence/api-ui-check.json). La façade ressemble à un bâtiment de rue générique, sans identité vérifiable de fleuriste : la fidélité artistique à cette consigne reste insuffisante et aucune note « photoréaliste » n'est revendiquée.

Le [profil matériel cloud](evidence/hardware.json) indique Linux, Blender 4.3.2, cinq CPU logiques et 34 GiB de RAM ; `nvidia-smi` et UE sont absents. Le temps total de mission est 585,28 s, incluant les deux assets et leur correction. L'assemblage Blender a pris 16,00 s avec un pic RSS échantillonné de 348,45 Mio ; la réouverture 1,27 s et 221,70 Mio. Ces mesures proviennent du reçu d'exécution et décrivent uniquement ce cloud, sans extrapolation à la RTX 4060 Ti. Le plan Qwen de la mission a généré sa réponse en 33,63 s sur le CPU explicite. Les quatre vérifications techniques restent distinctes d'un jugement artistique.

## Intégration

`POST /api/v1/game-studio/projects` lance une mission dynamique non bloquante ; `GET`, `cancel`, `resume` et le téléchargement d'artefacts restent les routes authentifiées existantes. Le reçu expose le plan, les sous-missions, les dépendances, les statuts, les refus et les versions. La page Game Studio montre ces données réelles. Les outils `game_studio.create/status/cancel/results` sont enregistrables dans `ToolRegistry` avec permissions explicites et propriété par workspace. L'enregistrement côté cerveau appartient à Claude et n'est pas fait dans cette branche.

La proposition de contrat à Claude est publiée dans [l'Issue #21](https://github.com/chadown62-glitch/apex-ia-/issues/21#issuecomment-6214667751). Le partage GPU doit passer par un protocole de quiescence demandé au propriétaire du cerveau, accusé de réception et bail partagé ; appeler directement `unload_all()` depuis un worker risque de libérer une inférence concurrente. Aucun handoff GPU en processus réel, aucun CUDA, UE5.8 ni launcher Windows n'est qualifié ici.

## Limites techniques

`ProjectService` et `TaskLoop` actuels supposent un harness de code à deux tâches et ne peuvent pas exécuter ces jobs Blender sans modifier leur contrat, dans le périmètre réservé à Claude. Game Studio réutilise plutôt son service parent, `MissionService`, les missions filles existantes et `ArtifactStore`. La génération reste limitée aux familles véhicule, bâtiment et fauteuil ; assemblage Blender générique et cadrage géométrique borné. Le cadrage n'est pas un juge esthétique calibré. Les demandes Unreal et les familles non prises en charge restent visibles comme bloquées. TripoSR, Vision, UE5 et la VRAM cible ne sont pas qualifiés par cette mission.

L'annulation interrompt Blender via l'événement transmis au worker, mais une génération Qwen déjà en cours peut attendre son délai d'appel (180 s maximum par tentative) avant de libérer le modèle. Le budget et la reprise parent ne décomptent pas encore cumulativement le temps de toutes les tentatives après un redémarrage ; cette limite doit être corrigée avant une autonomie de longue durée. Le résultat « Game Engineer PASS » n'est qu'un précontrôle GLB, sans simulation de véhicule.

Les contrôles ciblés API, plan, délégation, contrats Blender/UE et contrôleur passent (76 tests), ainsi que les tests de packaging/standalone (53), les 174 tests frontend, son build et `ruff`. Un wheel Python construit sous Linux contient `planning.py`, `vehicle_handoff.py`, `delegation.py` et `project.py` ; le frontend est empaqueté séparément par son build. **Le launcher APEX.exe n'a pas été exécuté sous Windows.** L'ancienne suite complète `test_tool_engine.py` compte 11 échecs dans ce cloud : le backend de sandbox conteneurisée renvoie `SANDBOX_UNAVAILABLE` aux tests qui exigent un conteneur démarré. Les tests de permissions/délégation Game Studio passent et aucun résultat de sandbox n'est simulé pour masquer cette absence.

Pour reproduire une nouvelle mission avec Blender et les poids Qwen déjà installés, le script existant `scripts/game_studio/demo_project.py` appelle l'API authentifiée dans un profil isolé : `python scripts/game_studio/demo_project.py --output /chemin/isole --manifest /chemin/coder-model.json --description "Crée une façade et un fauteuil puis assemble une scène."`. Il ne télécharge aucun poids ; le calcul CPU n'est choisi qu'explicitement dans ce cloud. Le [manifeste SHA256](evidence/file-manifest.json) identifie les preuves copiées dans cette PR. Les fichiers de travail complets restent dans `/workspace/game-studio-output/mission23-demo` et `/workspace/game-studio-output/mission23-vehicle-v2` tant que ce workspace cloud est conservé.

La prochaine expérience utile est de soumettre des consignes et références indépendantes au planificateur, puis d'évaluer la couverture sémantique et le juge visuel avec un jeu calibré. Sur le PC cible, il faudra qualifier séparément le bail GPU avec le cerveau, TripoSR CUDA et l'import UE5.8 d'un bundle véhicule dans un projet de test isolé, sans toucher `C:\GameProject`.
